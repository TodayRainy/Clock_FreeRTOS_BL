# Clock F407 项目编码规范

本文约束 `BL_W25Q_AB_VSCode` 中自行维护的代码。目标是让代码逻辑清晰、风格
统一、便于学习和面试讲解，同时避免过度抽象、过度封装和预见性防御编程。

本文规定代码应如何表达，不固定当前硬件参数和产品策略。Flash 地址、协议字段、
任务优先级、超时和版本号等具体值始终以当前源码与构建配置为准。

## 1. 适用范围

重点整理：

- `STM32F4_Bootloader/app/`；
- `STM32F4_Bootloader/driver/`；
- `WeatherClock/app/`；
- `WeatherClock/driver/`；
- `shared/`；
- 项目自行维护的 CMake、Python 和 C# 工具。

以下内容不主动格式化或改写：

- CMSIS 和 STM32 标准外设库；
- FreeRTOS；
- Mbed TLS 和 micro-ecc；
- 启动文件、链接脚本及其他第三方代码。

如果自研代码必须修复第三方代码中的真实问题，应作为独立修复提交，不与风格重构
混在一起。

## 2. 基础格式

- 使用 4 个空格缩进，不使用 Tab。
- 使用 Allman 大括号风格，函数和复合语句的左大括号单独一行。
- `if`、`for`、`while` 和 `switch` 后保留一个空格。
- 建议每行不超过 100 个字符；不可自然拆分的日志和注释最多 120 个字符。
- 简单单行分支允许省略大括号；包含多条语句、嵌套分支或易误读时必须使用大括号。
- 不把多个独立动作压缩到同一行。
- 十六进制地址使用大写数字，并为无符号常量添加合适的 `u` 后缀。
- 空行用于分隔不同逻辑阶段，不为每一条语句机械插入空行。

示例：

```c
bool firmware_slot_validate(uint8_t slot, magic_header_t *header)
{
    if (slot >= BOOT_SLOT_COUNT)
        return false;

    return firmware_slot_load_header(slot, header) &&
           firmware_slot_verify_data(slot, header);
}
```

## 3. 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件 | `snake_case` | `firmware_slot.c` |
| 函数和变量 | `snake_case` | `boot_state_save` |
| 类型 | `_t` 后缀 | `boot_state_t` |
| 宏和枚举值 | 大写下划线 | `BOOT_PHASE_TRIAL` |
| 对外函数 | 模块前缀 | `firmware_slot_install` |
| 私有函数 | `static`，名称表达局部职责 | `internal_data_valid` |
| 布尔变量 | 表达判断结果 | `header_valid`、`state_found` |

避免使用 `flag`、`temp`、`data1` 等无法表达含义的名称。`ret` 只适用于很短且返回
含义唯一的函数；较长函数应写明结果代表什么。

中断入口、CMSIS 弱符号和协议字段名称必须遵守平台或二进制契约要求，不能为了
风格擅自重命名。

## 4. 类型和数据布局

- 协议字段、持久化字段、寄存器和硬件地址使用固定宽度整数类型。
- 标准库缓冲区容量和内存操作长度优先使用 `size_t`。
- 纯成功/失败结果使用 `bool`；多种错误原因使用明确的错误枚举。
- 不修改输入数据的指针应使用 `const`。
- 不把可能未对齐的字节流直接强制转换为宽整数指针，应逐字节解析或使用
  `memcpy`。
- 持久化结构和协议结构必须使用固定宽度字段，并保留编译期尺寸检查。
- 不直接发送依赖编译器宽度的 C 枚举或未固定布局的普通结构体。
- `volatile` 只用于硬件寄存器或确实会被 ISR/硬件异步修改的对象，不能代替
  原子操作、队列、互斥锁或临界区。

## 5. 函数和控制流

- 一个函数负责一个完整且可命名的动作。
- 优先使用提前返回表达失败条件，减少多层嵌套。
- 不设置机械的函数行数上限；函数过长时先判断是否确实混合了多个职责。
- 不为只调用一次的两三行代码创建无意义包装函数。
- 状态机的重要阶段应由独立函数处理，入口函数负责顺序编排。
- 多个失败出口需要执行相同清理时，允许使用 `goto out`。
- 不通过宏隐藏普通函数逻辑，不使用会重复求值参数的函数式宏。
- 一个函数中的局部变量在相应逻辑附近定义，但同一阶段使用的状态可以集中声明。

## 6. 注释和 Doxygen

代码标识符和运行日志使用英文；文件说明、Doxygen 和设计注释使用中文，项目术语
如 Header、Trial、Rollback、Bootloader、CRC 保留英文。

### 6.1 文件级注释

自研 `.c` 文件应说明模块职责、边界和关键依赖：

```c
/**
 * @file firmware_slot.c
 * @brief 外部 A/B 固件槽的验证及内部 Flash 安装。
 *
 * 本模块负责读取、解密、校验和安装，不负责选择活动槽。
 * Trial 和 Rollback 状态转换由 bootloader.c 统一处理。
 */
```

### 6.2 对外接口

公开函数使用 Doxygen，按实际需要说明：

- 函数完成的动作；
- 参数和返回值；
- 调用前提；
- 对硬件和持久化状态的影响；
- 失败后的可恢复状态。

简单私有函数通常只需要一句 `@brief`，不机械填写没有信息量的 `@param`。

### 6.3 代码段注释

代码段注释优先回答以下问题：

- 为什么必须按这个顺序执行？
- 这里维持了什么状态不变量？
- 掉电或复位发生后，下次启动会怎样？
- 硬件手册要求了什么特殊时序？
- 为什么没有采用看起来更简单的写法？

推荐：

```c
/*
 * 在跳转前持久化消耗一次 Trial 机会。
 * 应用启动后立即掉电时，本次尝试也不会被重复使用。
 */
state->attempts_left--;
```

避免：

```c
/* 剩余次数减一。 */
state->attempts_left--;
```

注释必须随行为一起更新。无法解释代码目的时，应先理解或简化代码，而不是用猜测性
注释掩盖问题。

## 7. Bootloader 约束

以下规则属于设计不变量，不只是格式偏好：

- 正常上传和 OTA 不写活动外部槽。
- 擦除内部应用前，外部候选固件必须已经完成真实性与完整性验证。
- 内部应用 Header 最后写入，确保半成品不能被启动。
- 不可逆动作前先持久化能够指导下次启动恢复的阶段。
- 每个持久化状态转换都应能说明对应的掉电恢复结果。
- 自动 OTA 与人工维护权限明确分离。
- 安全决策只依赖受到签名保护的元数据。
- 维护接口不能绕过安装前的最终完整验证。
- Bootloader 不使用不必要的动态内存。
- 跳转应用前反初始化使用过的外设、中断和 DMA。
- 不在普通开发中修改 RDP、WRP、Option Bytes 或关闭 SWD。

## 8. FreeRTOS 和中断

- 高优先级任务必须阻塞、等待事件或适当延时，不能长期空转。
- ISR 只完成必要的读取、清标志和任务通知，不执行复杂解析或阻塞操作。
- ISR 中只使用 `FromISR` 系列 FreeRTOS API，并在需要时请求调度。
- 多任务共享 SPI、I2C 或 UART 时，必须明确总线所有权或同步方式。
- `xTaskCreate` 的栈参数单位是 `StackType_t` 数量，记录栈大小时不得误写为字节。
- 关键任务和同步对象创建失败不能继续运行。
- 看门狗由明确的健康监控路径统一刷新，避免多个喂狗点掩盖故障。
- 任务优先级和栈大小的调整属于功能/性能修改，不混入风格重构。

## 9. 错误处理

必须严格检查：

- 串口、网络和固件文件等外部输入的长度与格式；
- Flash、EEPROM、W25Q 和网络操作结果；
- 固件 Header、签名、Tag、摘要、地址和向量表；
- 可能永久等待的外设状态；
- 关键 FreeRTOS 对象创建结果。

通常不需要重复检查：

- 模块内部已经由调用约定保证的简单状态；
- 同一调用链刚刚完成完整验证且不会被并发修改的数据；
- 没有合理恢复方式、也不来自外部或硬件的纯假想错误。

原则是对外部输入和硬件故障严格，对模块内部可信路径保持直接。忽略某个硬件返回值
必须是有意识的决定，并在结果不直观时说明原因。

## 10. Include 和模块接口

- `.c` 文件优先包含自己的头文件，以暴露头文件缺少依赖的问题；随后是标准库、平台
  头文件和项目头文件。
- 头文件只暴露调用方需要的类型、宏和函数，不导出私有辅助对象。
- 头文件使用唯一 Include Guard，并保持 C/C++ 链接边界正确。
- 不依赖间接 Include 获得固定宽度类型、`bool` 或 `size_t`。
- 公共二进制契约集中在 `shared/`，应用和 Bootloader 不维护各自的重复副本。

## 11. 自动化与提交

- 自研 C 代码以 GCC 零警告构建为目标。
- `.clang-format` 只统一排版，不自动重排 Include，也不处理第三方目录。
- 不为了通过格式工具改变稳定的二进制布局或硬件时序。
- 一次提交只表达一个意图；注释/风格、逻辑修复和功能新增分开提交。
- 每批重构后检查 Git diff、固件大小和相关测试。
